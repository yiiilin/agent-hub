# Give one runtime exclusive ownership of an online Session

At most one runtime node may own and execute a Session at a time. The control plane records the owning node and a monotonically increasing ownership generation in PostgreSQL; Session commands, events, and Bundle commits carry that generation, and writes from an older generation are rejected. A heartbeat loss cannot reassign a Session whose latest state may still exist only on its owner: Agent Hub waits for that node to return or marks the Session recovery-failed after permanent node loss. Once a current Bundle is committed and ownership is released, any eligible runtime may acquire a new generation and restore the Session.

Ordinary Runtime deletion first places the node in a draining state: it receives no new Session ownership, and deletion cannot complete until every Session it already owns has committed a current Bundle and released that ownership. The administration interface lists the affected Sessions and requires an Administrator to enter the Runtime name before starting deletion.

Draining overrides the ordinary fifteen-minute idle window. An already idle Session begins bundling immediately. An active Turn and its Steering Messages may finish normally, but the draining Runtime starts no later Turn; as soon as that Turn ends, it stops app-server, creates a current Bundle, and releases the Session. Messages intended for a later Turn remain durably queued until another Runtime restores the Session.

A Session is drained once its current Bundle is committed and the original Runtime ownership is released; it does not need to have acquired a replacement Runtime. This permits safe deletion of the last Runtime. With no eligible Runtime available, Session history remains readable and later messages remain queued with an explicit waiting status until a Runtime joins.

If any Session cannot create or upload its current Bundle, ordinary deletion remains blocked, the Runtime stays draining, and Agent Hub retries while showing the failing Session and reason. An Administrator may cancel the drain, allowing the Runtime to accept work again; Sessions already released are not automatically assigned back. Alternatively, the administrator may explicitly switch to force deletion after reviewing the resulting recovery failures.

Force deletion remains available to an Administrator when a Runtime is irrecoverable or cannot finish draining. It is the explicit declaration that the node is permanently lost: Agent Hub immediately revokes its credential and invalidates its Session ownership generations, so a process that later returns under the deleted identity cannot heartbeat, publish events, or commit Bundles. The confirmation identifies every Session that will become recovery-failed; Sessions with a current Bundle remain eligible for another Runtime, while Sessions whose current state was not successfully bundled become Recovery-Failed Sessions.
