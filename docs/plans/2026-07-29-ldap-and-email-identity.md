# LDAP And Email Identity Delivery Plan

This plan implements the approved Hub email identity, Local Password Login, single global LDAP Directory, administrator provisioning, login throttling, and authenticated Integration email contracts in `docs/auth-spec.md`, `docs/integration-spec.md`, ADR-0032, and ADR-0033.

## Execution Rule

- Start every implementation task unchecked.
- Mark a task `[x]` only after its code, contract updates, and focused verification are complete.
- Add a new unchecked task directly below the task that exposes any required prerequisite.
- Modify the final initial schema directly. Do not add compatibility fields, old-database migrations, or a dual-read path for Hub `username`, `email_verified`, Mock OIDC, or nullable Hub email.
- Keep External Identity `external_user_id` and optional external username profile data; only the Hub User `username` is removed.
- The plan is complete only when every task is checked, real LDAP API/browser evidence is current, one workspace build passes, and the final read-only review has no valid blocking finding.

## Acceptance

- Every Hub User has one required current email and one Display Name; no live schema, DTO, API, or UI depends on a Hub Username or email-verification flag.
- Local Password Login, Password Registration, LDAP Login, first-user bootstrap, emergency Super Administrator access, policy lockout prevention, Session invalidation, and administrator provisioning follow `docs/auth-spec.md` exactly.
- Plain LDAP, StartTLS, and LDAPS work against a real directory with the approved warnings, validation, timeout, retry, query, mapping, and error behavior; no credential or raw directory identity reaches storage, logs, URLs, snapshots, or QA artifacts.
- Authenticated Integration flows cannot create a Hub User without a trusted email; existing external identity scoping, anonymous access, Session history, and Client Tool behavior remain intact.
- Focused tests, required SQLx evidence, frontend/SDK builds, targeted real-Compose QA, one workspace build, and the independent review all pass with no valid blocker.

## Rollback And Stop Conditions

- Rollback is code/image rollback plus database recreation. There is no in-place schema downgrade or old-database compatibility path in V1.
- Stop and reconfirm if the selected LDAP client cannot implement StartTLS or per-connection certificate verification policy safely, if another production path must create an email-less Hub User, or if supporting the confirmed behavior would require storing a service-account credential, permanent LDAP ID, historical email alias, or custom CA.
- Stop expanding LDAP deployment if the real test service cannot deterministically prove all three transport modes; do not replace required real-boundary evidence with a production authentication bypass or a fake success endpoint.
